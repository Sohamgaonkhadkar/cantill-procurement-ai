# Procurement interpretation and engineering decisions

The supplied brief and policy were read before implementation. Original files, extracted text, detailed private checks and sample results remain in `.private/`, outside Git and Docker build context. This document explains implemented rules; it is not a copy of the source PDFs.

## Decision framework

Three principles guide ambiguous cases: preserve exact financial evidence, prevent an uncertain input from creating an unsafe commitment, and make every material interpretation reproducible. A price benchmark is not supplier eligibility; a recommendation is not an approval; a grouping relationship is not a PO-consolidation relationship. Keeping these concepts separate prevents superficially plausible shortcuts from changing policy outcomes.

The choices below are implemented behavior. Where the policy is silent, the table explains the selected interpretation, business consequence and supporting test. Different evaluator preferences remain possible; these decisions are not presented as a hidden answer key.

## Amendment and calendar decisions

The brief requires two runs under frozen code but does not define a selected amendment's behavior for PRs dated before its effective date. Corvo separates two explicit modes. **Pinned historical processing** applies only the selected snapshot and retains pre-effective rows as NOT_PROCESSED with an explanation. **Run 2 calendar processing** uses the selected active amendment and earlier active policy dates; it never applies the amendment retroactively. Automatic selection uses the full active calendar. Batch Lab labels these choices; `/api/process-batch` accepts `policy_mode=pinned|calendar`, defaulting to pinned for compatibility. Runs capture their mode, calendar target and effective snapshots. The 14/15/16 November regression verifies both exports, grouping boundaries and replay.

Version names are identifiers, not chronology. Activating a version atomically supersedes active versions with the same effective date under the policy-calendar lock, with explicit audit entries. Earlier dates remain available. Any ambiguous same-date active snapshots supplied directly to the engine are rejected instead of choosing a lexicographic winner. Pinned historical replay remains possible for superseded versions. Tests cover `5.9`, `5.10`, `6.0` and a descriptive amendment name.

The bounded amendment compiler validates the old value in “from A to B” instructions and preserves exact comparison operators and decimal currency values. Unsupported clauses remain unresolved. A saved JSON edit is insufficient evidence of reconciliation: review requires one confirmed mapping per original unresolved clause, the intended meaning and scope, changed executable paths, effective date, relevant priority and evidence. Recognizable plant/category/route/value facts are checked against the saved definition. An unrelated weight edit, reason-only edit, missing mapping, wrong boundary or unconfirmed clause cannot satisfy review. Unknown legal/commercial meaning still requires human judgment; these checks do not claim to prove unrestricted natural language.

New rules can shadow contract, Capex and emergency handling. Conservative symbolic predicate analysis reports possible overlaps and example facts. It does not infer real item/category relationships or claim every symbolic example is an actual request. New or reprioritized overlapping rules and incomplete analysis require an explicit reviewer acknowledgment. The structured rule helper requires an unused priority chosen by the operator. Simulation establishes the actual batch impact. Review is bound to the current definition hash; saving further edits clears review and clause evidence.

## Independent audit and access boundaries

The submission checker remains read-only. CSV-only checks verify structure and identity multiplicities. Optional immutable run JSON and master snapshots enable independent arithmetic, grouping-window, policy-date, supplier-price, rank-order, ceiling and PO-window invariants without importing the procurement engine or its ranking implementation. Preferred-supplier date/version verification also requires explicit metadata because the required four-column CSV cannot encode those fields. Missing evidence produces warnings, not a claim of certification. This is selected invariant validation, not a second general policy interpreter.

Public built-in accounts operate on the isolated fictional schema. Demo CSV processing rejects plants or explicit catalog codes outside fictional masters before persistence; known challenge identifiers are also blocked in demo chat and amendment text. Arbitrary free text cannot be classified perfectly as private, so users must still obey the fictional-data notice and consent boundary. Private assessment processing requires an individual account. Evaluator credentials remain private; use an approved channel if assessment access must be shared. Never place them in the repository, frontend or public password list. The main URL remains the single entry point.

Public signup is restricted to fictional data in production. Previously, a self-registered Requester could reach authenticated master-data endpoints; having a password alone did not establish assessment authorization. The server now rejects assessment self-registration even if its environment flag is accidentally enabled, and denies legacy self-registered assessment sessions and credentials. Owner-provisioned individuals carry an explicit scope; these accounts retain assessment access. Records are preserved. New personal demo accounts use their own masked passwords and the isolated namespace on the same login page. A workspace selector distinguishes these from privately provisioned assessment identities. Development signup remains available for isolated tests.

## Ranking formula

For each item and as-of date, eligible suppliers are Active suppliers with a PO in the preceding configured 548 days or an item contract that has already started. For each supplier, let `n` be its qualifying PO count, and `m` the largest count among eligible suppliers. Frequency is `log(1+min(n,10)) / log(1+min(max(m,1),10))`. This is bounded and normalized within the item, so five purchases represent stronger familiarity than a single contract-backed purchase even if the item's overall history is sparse.

Recency is 1 for a last PO within 90 days, 0.5 within 365, otherwise 0, including no PO. Contract score is 1 for any started item contract (expired included). Delivery is `on_time_pct/100`, quality is `quality_rating/5`. Multiply those normalized values by 25, 25, 20, 15, 15 respectively, then sum. Float logarithms affect ranking scores only; financial arithmetic never uses float. Parameters, weights and time tiers are editable policy data.

Reference price uses the supplier's latest PO within 548 preceding days; ties break by PO number then supplier ID descending. Without such a PO, use the latest started contract by start date then contract ID descending. Preferred suppliers are ranked independently of whether their contracts currently have ceiling. This permits a contract supplier to remain a good sourcing candidate after ceiling exhaustion.

## Current tradeoffs

Security audit update: public Admin/Buyer access is confined to the isolated fictional demo. Assessment access requires a private individual identity; evaluators have an evaluation scope that permits procurement/policy workflows but blocks user administration and bulk master-data replacement. Assessment registration is disabled; fictional-demo registration is independently configured. Session-signing keys are rotated when retiring public shared access; assessment credentials never appear in authentication options; the demo exposes only its fictional-role passwords.

Malformed CSV headers are rejected at intake. Allowing duplicate quantity columns would let a parser overwrite a financially material value before any policy logic sees it. Final output verification is separate: the read-only submission checker tests schema, line identity, decimal/action consistency and optional Active-supplier membership without recalculating financial decisions.

The conservative amendment compiler recognizes complete supported limit, window, supplier-count and scoped rule statements. Master-data scope resolution rejects ambiguous values. Unsupported language remains visible and blocks ordinary review until explicit manual verification after structured authoring. Registered-fact rules can be entered through validated structured authoring and JSON without application code changes. Approval requires source review. Live chat retains bounded deterministic intake and local retrieval; the isolated fictional demo additionally has configured Gemini assistance. No OCR service or signature-authenticity verifier is implemented. Arena's frontend is integrated against the real API; verification scope and release-specific results are recorded in VALIDATION.md.

The source brief is an individual assignment. No subagents or other candidates' implementations were used. Deadline and publication obligations require human submission of the assessment form; the application cannot submit the blind test before receiving its data.

Numeric resource bounds: financial arithmetic uses Decimal precision 64. Inputs are finite, at most 10^18 in magnitude, 24 coefficient digits and 12 decimal places; malformed comma grouping and excessive exponents fail validation rather than reaching arithmetic or JSON serialization. These are operational bounds, not policy thresholds.


## Additional hardening decisions

- **Approval freshness:** historical runs remain replayable/exportable, but a purchasing action is rejected when a newer active policy applies to the requirement date. Reprocess before approving. Activation and commitment coordinate through a transaction-scoped policy-calendar lock.
- **Independent review:** an amendment can require additional sourcing approvals by item type. Votes are persisted under the requirement lock; an account can vote once, and no action or source commitment exists until quorum. Overrides cannot bypass the quorum. The original v5.0 policy still requires its original single buyer approval.
- **Source reconciliation:** retain both extracted-text and exact-upload SHA-256 evidence. Conflicting or unsupported clauses remain visible. Manual review requires a saved substantive DSL change and explicit acknowledgement; this proves deliberate human intervention, not automatic semantic completeness.
- **Supplier exclusions:** amendments may narrow Active supplier eligibility or exclude specific suppliers' contracts. Ranking weights cannot reintroduce an excluded/blocked supplier. Valuation history remains distinct from supplier eligibility as required by the original policy.
- **Spreadsheet exports:** escape formula-leading text cells, including identifiers, descriptions and explanations. Genuine numeric decimal fields retain their original numeric representation. Ordinary assessment output is unchanged; hostile spreadsheet text is intentionally escaped.
- **Resource budgets:** persist per-account batch, document-upload and chat operation budgets across workers. Return 429 with Retry-After; keep logout available. Limit a chat to 400 stored messages and ask for a new session rather than grow state indefinitely.
- **Lock ordering:** take catalog coordination before contract locks and policy-calendar coordination before requirement locks. Bulk import takes the exclusive catalog lock before checking existing commitments. A process-local lock alone is not the PostgreSQL safety mechanism.
- **Frontend precision:** UI formats decimal text directly, including numbers outside JavaScript's safe integer range. Financial decisions remain server-owned. Pending approval votes are described as pending reviews, with no synthetic success state.

## AI and interface boundaries

- **Direct free-tier provider:** use server-side Gemini credentials with a reviewed model allowlist. Do not enable AI Gateway, billing, automatic paid/provider fallbacks or a local inference dependency.
- **Hard egress boundary:** require the isolated demo database, an external-call flag, per-turn fictional-data acknowledgment and approved source provenance before creating an external client. Live conversations remain local even when a key is accidentally present.
- **Evidence before fluency:** include complete clause conditions and policy parameters, generate citation identities on the backend and reject unsupported numeric/entity claims. Show local evidence when synthesis fails.
- **Durable turns:** persist request identity, lease and revision; release database transactions before network calls and revalidate actor and draft before committing. Retry of a completed confirmation returns the original run.
- **Source revisions:** a newly uploaded draft does not hide its approved predecessor. Review supersedes the previous approved revision. An active policy's structured index is updated locally during activation.
- **Interface continuity:** retain Arena's original visual components and five-stage 3D Decision X-Ray, with a 2D evidence alternative. Structured policy authoring and JSON use the actual registered-fact schema. Visual presentation never changes procurement calculations; backend algorithms, migrations and regression tests are preserved.
